# AgentRunner — 开发流程（PROCESS）

**这是什么**：本项目的产品定义与开发管理方式。核心思想：产品由三层
文档定义（journey → spec → design），**文档描述已经成立的事实，不
领跑代码**；改动想清楚就做，落地以 journey 级端到端测试验收。真正
的硬纪律只有三条：不变量不许绕、check.sh 不许红、双闸门不许缺腿。

---

## 一、三层产品定义

```
第一层  JOURNEYS.md   端到端 user journey —— 产品要做什么
   ↓ 拆分
第二层  SPEC.md       功能点登记簿 —— 有哪些功能、什么状态、验收锚在哪
   ↓ 衍生
第三层  DESIGN.md     架构 —— 功能点如何成立、为什么这样设计
```

- **第一层回答"为什么存在"**。journey 是端到端的使用故事，定义产品
  边界；一个功能不被任何 journey 覆盖，先怀疑它该不该做。
  第一层有一个**伴生物**：**不变量**（DESIGN §15 已定决策表与各章
  粗体条款）——journey 覆盖"功能"，不变量覆盖"性质"（崩溃不丢输入、
  journal-first、凭据红线这类横切保证，没有任何单条 journey 的情节
  能压到它们）。两者共同构成需求层。
- **第二层回答"有什么"**。功能点从 journey 拆出、按功能域组织、可
  继续向下细分；每条登记：状态、journey 来源、验收锚（哪条测试证明
  它 work）。SPEC 是"正面清单"，GAPS 是它的镜像"负面清单"（审计件）。
- **第三层回答"怎么成立"**。DESIGN 是架构 source of truth，承载语义
  契约与不变量。功能点的实现方式由它裁决。

**支撑件**（不属于三层，服务三层）：

| 文档 | 职责 |
|---|---|
| `QA.md` | journey 级**真实 API** 验收场景菜单（脚本在 `qa/`），第一层测试的可执行形态 |
| `GAPS.md` | 审计件：journey × 设计/实现 的缺口登记（负面清单） |
| `LOG.md` | 决策台账（理由、坑、接受不修的偏差），只追加 |
| `archive/` | 已完成计划与过时文档的封存（只读） |

**冲突裁决顺序**：产品意图以 JOURNEYS 为准 → 实现状态以 SPEC 为准 →
语义契约以 DESIGN 为准（含 §17 实现状态注记的诚实偏差）→ 归档件永远
让位于活文档。发现两份活文档冲突 = 缺陷，当场修（并查第三份），
不带病共存。

## 二、改动怎么进来

**默认路径：想清楚就做。** 没有前置文档、没有工作纸、没有批准闸。
直接改代码，`./scripts/check.sh` 全绿就提交推送。

只有两种情况必须先停下来写字：

1. **动 DESIGN 不变量**（§15 决策表 + 各章粗体条款）——走第四节的
   不变量变更流程。这是唯一的硬闸，因为绕过它的代价是横切保证失守。
2. **改变产品边界**（新 journey，或既有 journey 的形态变了）——先在
   JOURNEYS.md 落一条。一两句话讲清用户要什么即可，不是文档工程；
   目的只是别做出没人要的功能。

**文档跟着代码走，不领跑。** 三层文档描述**已经成立**的事实。改动
落地时若它改变了某层的事实，就在**同一个 commit** 里更新那一层；没
改变就别动。**禁止为了流程完整而产生纯文档提交**——工作纸、收口件、
台账条目这类中间载体一律不写。

**LOG.md 只记会影响后续判断的东西**：决策的理由、踩过的坑、接受不
修的偏差。不记"我做了什么"，那是 git log 的职责。

**review 按需做，不按规模做**：拿不准正确性/并发、安全或契约时才拉
对抗 review，且 review 结论直接变成代码改动，不落单独的评审文档。

> **`docs/increments/` 已冻结**（2026-07-28）。旧工作纸制度要求每个
> 增量起草 → 裁决 → 收口 → 归档，产出近百份中间文档和大量纯文档
> 提交，而文档本该描述既成事实。典型反例：INC-102 全套工作纸与收口
> 件落地后被整体 revert，随后又是三版零实现的设计稿。目录保留为历史
> 只读，不再新增。

## 三、执行协议（实施期纪律，承自 v1 PLAN §0.5 与 v2 PLAN §0）

1. **session 开始**：`git fetch origin main` + fast-forward，永远在
   最新代码上工作。
2. **一个改动 = 一个可合并提交**：代码 + 测试 + 受影响的文档行齐活，
   `./scripts/check.sh` 全绿才 commit；消息讲清**做了什么、为什么**，
   格式自便（跨多步的工作可用 `<主题>: <摘要>` 串起来）；立即 push
   `origin/main`（只用 main）。不留未推送提交、不留未提交改动过夜。
   **一个提交要能独立说明自己的价值**——凑数的中间态、纯仪式的文档
   提交不要产生。
3. **回归红线**：全部单元测试 + v1 acceptance 26 场景 + 既有 QA 场景
   在每一步保持绿；行为变化一律 opt-in 落地，不破坏既有形态。
4. **双闸门**（每个功能点两条腿，缺一不可）：
   - **闸门 A：scripted 孪生**——确定性、离线（scripted/routing
     provider + crash 注入），进 `check.sh` 常跑；
   - **闸门 B：真实 API QA 场景**——QA.md 菜单逐字照做（断言只钉
     runtime 红线，不钉模型措辞；一次重跑规则适用），结果归档
     `qa/runs/<日期>-<QA号>/`。B 闸失败 → 归因（runtime bug / prompt /
     环境）；runtime bug 必须修复后重跑。
5. **设计冲突**：实现中发现 DESIGN 语义走不通 → **停下**，在 LOG 写清
   冲突，修订 DESIGN 与实现**同一个 commit** 落地——禁止代码悄悄绕。
6. **台账**：影响后续工作的决策/偏差/接受不修，一律记 LOG.md。
7. **术语纪律**：引入新术语、或改变既有术语的含义，入档前必须先做
   外部主流用法调研——与主流对齐，或在 LOG 写明偏离理由；裸词存在
   行业歧义时必须带限定词（案例见 LOG 2026-07-05 turn/step 两条）。
8. **首用旅程闸（QA-0724-goal 事故沉淀，硬性）**：任何用户可见的新功能/
   新形态（或其入口/呈现的重构），在标记 ✅ 前必须以"真实用户第一次
   用它"的完整旅程真跑一遍——共享环境、真实 API、从创建入口一路到
   读完结果的全生命周期，**turn 进行中与终态各截屏**。终态屏按四条
   清单逐项审，任一不过即为 bug：
   ① 同一事实一屏最多陈述一次（chip/banner/action row/面板重复=bug）；
   ② 无永久 loading/骨架/占位残留（含 live 流事件期间的呈现）；
   ③ 无贴边、溢出、挤压布局（含桌面全宽度，不只窄屏）；
   ④ 文案与真实能力一致（不承诺不存在的东西，不谎称状态）。
   既有功能被这条闸追溯揪出的问题直接当 bug 修。
   背景：goal×plan 首次真实使用即暴露 5 类问题，而此前数十轮 QA 全部
   走"预设最顺路径"（goal 只在 default mode 测过），组合空白 + 终态
   信息架构从未被审过。
9. **组合矩阵与常驻注入纪律（QA-0724-goal 事故沉淀）**：
   - 功能落地/修改时，必须列全它与**运行模式**（plan/default/
     acceptEdits/bypass）及自身形态维度（如 goal 的 verifier 三态）的
     组合矩阵：语义不成立的格子在文档写明拒绝/降级方式，成立的格子
     至少 scripted 孪生覆盖一格一断言，有交互疑点的格子进 QA 菜单
     （模板见 QA-93）；
   - 任何**常驻注入文本**（mode 系统后缀、goal/loop 注入、continuation、
     工具 description）的增改，必须列出它与其它常驻注入的同屏组合并
     逐对检查指令冲突——两条常驻指令不得让模型二选一（案例：plan 后缀
     "就绪即调 exit_plan_mode" × goal "keep going until met" 让模型连烧
     3 turn 申请没人要的 exit）。

## 四、不变量变更流程（硬性）

DESIGN 的不变量 = §15 已定决策表 + 各章粗体条款。动它们必须：

1. **停下**当前实施；
2. **说清四件事**（写进 LOG.md 的那条决策里即可，不另起文档）：旧不
   变量原文 / 为什么必须动 / 新表述 / 波及面（哪些代码、测试、文档
   跟着变）；
3. **单独 review**（至少契约视角），通过后 DESIGN 修订与实现同
   commit 落地。

禁止的路径只有一条，但要写明白：**代码先绕过不变量、文档事后再补**。

## 五、测试体系速览（谁证明什么）

| 层 | 位置 | 证明什么 | 何时跑 |
|---|---|---|---|
| 单元/集成 | `internal/**/*_test.go` | 机制正确 | 每步（check.sh） |
| scripted 孪生 | 同上（scripted/routing provider） | 功能点确定性端到端 | 每步（check.sh） |
| crash 注入 | 同上 | in-doubt/恢复不变量 | 每步（check.sh） |
| acceptance | `e2e/`（26 场景） | v1 各阶段能力回归 | 每步红线 |
| QA 场景 | `qa/run-qa*.sh`（QA.md 菜单） | journey 在**真实 API** 下 work | 闸门 B / 发布前扫验 |

新功能的验收锚按此分层落位：功能点 → 孪生 + QA 场景；性质 → crash
注入/单测。

**登记簿真实性（硬性，2026-07-10 复盘落地。事故：v1 S3.6c 跃迁表三条边
只锚一条，default↔acceptEdits 用户命令入口静默缺失、SPEC 却记 modes ✅，
直到用户追问才暴露——见 GAPS G29。机械检查 `scripts/lint-docs.sh` +
`scripts/lint-wiring.sh`，都进 check.sh）**：

1. **锚必须可执行**：SPEC ✅ 行的锚必须点名真实存在的 `Test*` / `QA-n`；
   档期名（S2、INC-n）与叙述文字不是锚。存量弱锚记
   `scripts/spec-anchor-debt.txt` 基线，只减不增（G30 燃尽）。
2. **✅ 判据 = 用户可达**：有用户入口的功能，锚必须包含驱动该入口的
   测试/QA；"数据表/事件底座齐但入口未接线"不得记 ✅——如实记 ❌/⚠️
   并同 commit 挂 GAPS 条目。枚举型交付物（跃迁表每条边、mode 每个值、
   命令面每条命令）逐项对锚，裁掉的项显式声明。
3. **接线审计**：deadcode（从两个 main 做 whole-program 可达性）对比
   `scripts/deadcode-baseline.txt`；新增不可达导出拒绝提交，基线增行须
   LOG 给理由。**有测试调用 ≠ 已接线**——测试可以只断言数据表
   （TestModeTransitionTable 三条边全绿而入口零接线，即本次事故）。
4. **审计四问**：对表类审计（PARITY/GAPS/走查）对有状态功能按生命周期
   四问——可设置？可见？**可变更？谁可变更？**——按问记状态，不按
   功能名整行 ✅。
5. **GAPS 编号唯一**（曾重号 G24/G25，2026-07-10 更正），linter 强制。

## 六、归档纪律

见 `archive/README.md`。要点：计划关闭/文档被取代即移入 archive 加
头部注记，正文不动、引用不修、永不删除。
