哲学层（constitution）

产品定位

选择：Coding Agent 之上的项目记忆 / 上下文 / 任务协调层——自己不做执行 runtime。

代价
  • 命脉握在外部 agent 手里（能力、接口变动都要跟）。
  • 执行过程不可见（被 C9 强化），调试问题要去外部系统。
替代方案
方案产品没选的原因
自研 agent runtimeDevin、agentrunner重复造轮子，偏离"记忆层"价值
纯项目管理（不执行）Linear、Jira缺了闭环里"委派→回流"的那半环
先例
我们=记忆层Devin=自研执行Linear=管理不执行（2025 起也接 agent 委派）

文件即真相

选择：项目知识全部落盘 Markdown+frontmatter，应用只是视图；不带 DB 也能被人/agent 读懂续作。

代价（引入的问题链）
  • 没有 block id → 锚定难 → 智能匹配 A7。
  • 外部可绕过应用直接改文件 → 冲突合并 → D1。
  • 查询/聚合慢 → SQLite 索引（可重建）。
  • chat、显示顺序、运行态放不进文件 → 伴随库。
  • 无损写回约束限制编辑器块类型 → 白名单。
替代方案
方案产品没选的原因
云端数据库为真相Notion、Linear知识被锁进产品，agent 要学 API 才能用
本地对象库/CRDTAnytype同上，且失去 git/grep/编辑器生态
先例
我们=纯文件Obsidian=纯文件（同路）Logseq=文件+DB 索引（近路）Notion=云 DB

一切皆文档 · 没有目录

选择：树里每个节点都是文档；"特殊类型"= 可选 frontmatter type；没有目录/模块概念。

代价
  • 嵌套需要落盘表示 → 同名同级目录。
  • 行级微文档会炸树 → 不进树 → 到达路径要补（搜索/祖先高亮）。
  • 失去强 schema 的批量查询力（"所有 P1 bug"靠索引而非表）。
替代方案
方案产品没选的原因
页面嵌套 + database 两套体系Notiondatabase 是第二套模型，违"少而稳"
文件夹 + 文件Obsidian目录成为第二种对象，语义分裂
强类型对象（issue/epic）Linear、Jira回到表单式管理系统，被 v0.6 之前的轮次否掉
先例
我们=纯文档树Notion=页面+databaseWorkflowy=纯 outline（更极端）

结果回流闭环

选择：session 产生经验 → 沉淀为文档（Attempt/Lesson/状态）→ 成为下次委派的 context。

代价
  • 写回格式必须稳定（文件契约就是 API，坏一处 agent 全乱）。
  • chat 里的好内容若不回流会流失——靠"沉淀成文档"纪律兜底（接受）。
替代方案
方案产品没选的原因
对话历史即记忆ChatGPT memory不可审计、不可编辑、不可移植
自动记忆库（向量）各类 RAG 产品黑盒；与"文档可读可改"的定位冲突
先例
我们=显式文档回流Devin=knowledge 条目Claude Code=CLAUDE.md/skill 沉淀（近路）

负空间（刻意不做）

选择：不做 diff 管理、session 浏览器、Inbox 页、DAG workflow、用户/权限体系。

代价（引入的问题链）
  • 不做 Inbox → 动静感知真空 → 铃铛。
  • 不看 diff → 改动可见性弱 → 高亮 + git 兜底。
  • 顺序 Loop 表达力上限（做不了并行/条件流）——接受。
替代方案
方案产品没选的原因
全功能平台化Jira、Notion（越做越全）分散焦点；16 轮决策一路在做减法
DAG workflown8n、Zapier、GitHub Actions用户明确砍掉（决策 #02）
先例
我们=做减法Linear=同样以克制著称
结构与存储层

任务即文档（含惰性物化、镜像行）

选择：每个 task 的身份是一个 .md；呈现保持一行 to-do；首次需要身份时才物化；物化后文档为准、父行是镜像。

代价（引入的问题链）
  • 轻任务可能变重 → 惰性物化解决。
  • 镜像行与文档双真相 → 文档 canonical、应用维护镜像；外部改镜像可能短暂漂移（对账兜底）。
  • 微文档数量多 → 不进树 + 搜索到达。
替代方案
方案产品没选的原因
任务=DB 行/结构化对象Notion database、Linear、Jira与文档割裂，portability 差
任务=纯文本行Obsidian Tasks、TaskPaper挂不住 attempts/lessons 等历史
三级渐进升级（行→widget→文档）我们的 v0.6 方案升级迁移身份，锚点会断——v0.7 废弃
先例
我们=任务即文档GitHub issue=半文档（md body）近路Linear=强 schema

落盘结构与命名

选择：文档永远是单文件；子文档放同名同级目录；文件名=标题（中文保留，rename 改写入链）；assets/ 图片、.contextcenter/trash 软删。

代价
  • rename 要全库改链接（应用负担，外部改名靠 id 对账）。
  • 同名冲突要 -2 后缀；跨平台文件名字符集要处理。
  • 文件→目录升级由应用自动做（首个子文档出现时）。
替代方案
方案产品没选的原因
id 做文件名，标题存文件内部分 Zettelkasten 工具目录不可读，违"人能直读"初衷（用户已否）
目录+index.md 表示每个文档Hugo/docs 站点惯例每个文档都成目录，太重（v0.7 曾用，v0.8 废）
先例
我们=标题即文件名Obsidian=同路Notion=无文件概念

SQLite 伴随库

选择：放不进文件的进 SQLite：chat、树顺序、节点应用态、运行态、时间戳、计数器、可重建索引。

代价
  • 两储一致性边界要守（知识永远不许只活在库里）。
  • 删库丢 chat 历史/顺序——接受（知识已回流文档）。
替代方案
方案产品没选的原因
全进文件（chat 伴生 .md）部分插件生态做法对话噪音污染文件树，git 全是 chat diff
全进数据库Notion、Linear违 C1
先例
我们=文件+伴随库Obsidian=同构（.obsidian/ 存应用态）Logseq=同构

Attempt = 结果摘要（无 diff）

选择：一次委派记一条 Attempt：状态/outcome/摘要/lesson/best 标记；不存 transcript、tool calls、diff。

代价
  • 排查"agent 为什么失败"要跳外部系统（View run 外链）。
  • 摘要质量依赖写回方（agent 按契约自报）。
替代方案
方案产品没选的原因
全量执行记录+diffCursor、Devin、agentrunner用户明确否掉（决策 #05）：关心结果不关心过程
PR 为结果载体Codex cloud、GitHub代码评审自有工具，本品不重复
先例
我们=摘要Codex=PRDevin=全过程可看

display id 与 Lesson

选择：#N（任务）/#BUG-N（缺陷）project 内连续、永不复用；Lesson=来源同级的 type:lesson 子文档，委派时按引用自动携带、卡片内可增删。

代价
  • 跨 project 移动要重新编号（frontmatter 记 moved_from）。
  • lesson 不做自动相关性检索（Stage 2+），可能漏带——先靠显式引用。
替代方案
方案产品没选的原因
全局唯一 id（ENG-123）Linear、Jira我们 project 即边界，够用且短
向量检索自动补 lessonRAG 类黑盒+成本，MVP 显式引用可控
先例
我们=项目内编号GitHub=repo 内编号（同路）
编辑与交互层

Block 编辑器 + 块白名单

选择：Notion 式 block 编辑（拖拽/转换/slash/markdown 快捷输入），块类型限定为"能无损写回 Markdown"的白名单。

代价
  • Notion 的高级块（database view、多列、同步块）做不了——被白名单挡住。
  • 编辑器工程量是全项目最大单件；库选型（TipTap/Lexical/自研）待工程决策。
替代方案
方案产品没选的原因
源码/实时预览混合 MD 编辑Obsidian、Typora对非程序员不够"Notion 般顺滑"，slash/widget 难嵌
富文本（非 MD 语义）Google Docs写回 Markdown 必然有损，违 C1
纯 textarea + 预览GitHub issue体验与"始终可编辑"矛盾
先例
我们=block+MD 白名单Logseq=outliner+文件（近路）Notion=block+云 DB

Chat 文字引用

选择：选区以 blockquote 纯文字进输入框；可编辑可拼接；不做引用 chip widget。

代价
  • 引用与原文的绑定变弱（正是 A7 锚定要解的）。
  • 长引用占输入框空间（可手动删减——这也是灵活性的一面）。
替代方案
方案产品没选的原因
引用 chip（结构化）ChatGPT 选中回复、我们 v0.7 mock不可编辑、不可拼接，用户明确否掉
锚定评论（挂在原文上）Google Docs、Notion 评论是"批注"不是"对话"，Chat 已定常驻右栏
先例
我们=纯文字 quoteChatGPT=chipNotion=块锚定评论

三栏布局：右栏 Metadata + Chat 常驻

选择：树 / 画布 / 右栏双区（上=当前页 frontmatter 渲染，下=本页 chat）；点开哪个文档右栏就换谁。

代价
  • 横向空间紧（内容列被压到 ~708px，小屏右栏要收）。
  • chat 绑定当前页 → 跨页动静要靠铃铛补。
替代方案
方案产品没选的原因
属性内嵌页顶Notion结构化字段多时占正文；右栏更稳定
点击对象弹 Inspector我们 v0.7 mock、设计工具用户裁决：右栏应始终显示"当前页面"的信息
chat 全局单窗Cursor、ChatGPT失去"对话跟着文档走"的上下文性
先例
我们=页面级右栏Cursor=全局 chat 栏Notion=页顶属性+右滑评论

Notion UX 批量继承（28 项）

选择：凡 Notion 有对应交互一律照抄：即点即建、hover 菜单、拖拽移动、cmd+K、emoji picker、Trash 软删、Turn into、属性面板、@mention、折叠记忆、快捷键子集、空态占位……

代价
  • 被 Notion 的心智绑定：偏离处（右栏、文字引用、无目录）要自己扛认知成本。
  • 照抄也意味着继承其交互密度的实现成本（hover 态、拖拽是工程大头）。
替代方案
方案产品没选的原因
键盘优先极简 UXLinear受众是"文档心智"用户，Notion 习惯迁移成本最低
逐项自研交互—52 项 gap 里 28 项白拿，没理由不拿
先例
我们=Notion 系Linear=键盘系Obsidian=编辑器系

动静感知：铃铛 + 蓝点

选择：顶栏铃铛（计数/转圈）+ popover 事件列表 + 树行蓝点；popover 非页面，守 C9。

代价
  • 事件多了 popover 会挤（无归档/过滤——到那天再议，可能逼近 Inbox 红线）。
替代方案
方案产品没选的原因
独立 Inbox 页Notion、Linear、GitHub违 C9（用户砍过独立 Message 导航）
只有树行蓝点Slack 侧栏未读树折叠时看不见，无统一时间线
不提示Obsidianloop 跑完无从知晓，违闭环体验
先例
我们=铃铛浮层Notion/Linear=Inbox

移动端范围（D15）

选择：阅读优先 + 四动作（树抽屉 / 阅读 / chat / 长按引用）；编辑纯文本级；hover/拖拽以 ⋯ 菜单替代。

代价
  • 移动端不能做结构编辑（挪块/转块）——接受，主场景在桌面。
替代方案
方案产品没选的原因
全功能移动编辑Notion mobile成本极高，V1 不值

Agent 执行层

文件即 API：双向集成

选择：外部 agent 直接读写项目目录（AGENTS.md 说明契约）：读根文档渐进披露、追加 attempt、建 lesson/子文档。

代价
  • 格式即契约：文件约定一变，所有 agent 的"技能"都要跟着改。
  • 无法细粒度鉴权（文件系统级全有或全无）——单人 MVP 接受。
替代方案
方案产品没选的原因
REST/MCP API 集成Notion API、Linear APIagent 要学接口；文件是 coding agent 的母语
只出不进（单向）多数"AI 增强"工具断了回流闭环的后半环
先例
我们=文件契约Claude Code=CLAUDE.md/AGENTS.md 同路Notion=API

外部直改 + 事后可撤（含 D1 合并）

选择：外部 agent 改动/建档直接生效；应用实时高亮、chat 留痕、undo、铃铛；人机同文档冲突走块级合并（冲突块保本地+外部版可采纳），不弹窗。

代价
  • 坏改动会先落盘（靠 undo/trash/git 兜底）。
  • 块级合并是同步机制里最难写对的部分。
替代方案
方案产品没选的原因

PR 制（分支+评审）Codex cloud面向代码合适；对"项目记忆文档"太重
锁文件（编辑期独占）传统协同阻断 agent 长任务，体验差
先例

锚定 = 智能匹配 + 降级

选择：锚 = 引用文字 + 就近标题路径；Apply 时模糊匹配；置信不足提示手动放置。不注入 block id。

代价
  • 偶发失配（大改后）→ 降级到"手动放置"，接受。
  • 匹配器要调（容错阈值、重复文本消歧）。
替代方案

顺序 Loop（含 D8/D9/D10 语义）

选择：Loop=文档，队列=正文链接列表；顺序执行；失败暂停（Retry/Skip/Stop 红条）；Pause=跑完当前项；blocked 跳过并记录；一个 task 同时只一个 attempt。

代价
  • 无并行/条件分支（大批量修 bug 吞吐受限）——接受，换可理解性。
  • 中断外部 session 不保证成功（标 abandoned）。
